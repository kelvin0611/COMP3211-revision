寫 requirement 嘅步驟

  1. 判斷類型：系統「做咩」→ FR；「做得幾好／有咩限制」→ NFR。
  2. 用 shall（必須）或 should（想要）。主語係 system 或 user：「The system shall…」「Users shall be able to…」。
  3. NFR 一定要有數字：時間、百分比、負載、測量期間（例如「within 2 seconds for 95% of requests with 10,000 concurrent users」）。
  4. 加括號 rationale（L4 指引，Asm1 注意事項都有講）。
  5. 檢查：一條 requirement 只講一件事；冇電腦術語；可以設計 test 判斷 pass／fail。

二、筆記：由零講起

一分鐘重點
  • Requirement = 系統要提供嘅服務 + 運作上嘅限制。RE = 發現、分析、記錄、檢查呢啲 requirement 嘅過程。
  • 3 個 generic activities：elicitation、specification、validation（spiral，交錯重複）。
  • Elicitation 4 stage：discovery & understanding → classification & organization → prioritization & negotiation → documentation。
  • Validation 5 check：validity、consistency、completeness、realism、verifiability。

1. Requirement 同 requirements engineering

一句講完

Requirements 係系統應該提供嘅服務同運作時嘅限制。RE 係發現、分析、記錄同檢查呢啲服務同限制嘅過程。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解重要（L4 五點）
  1. 令所有人有同一個理解。
  2. 話俾團隊知做咩、喺咩限制下做。
  3. 令成功可以量度、可以 test。
  4. 減少失敗、重做同法律風險。
  5. 做 project 管理嘅基礎。
圖解：requirement 喺 process 嘅位置 例子

Agile 唔寫詳細 system requirement，用 incremental RE 同 user story；適合商業系統，但對好多其他系統有問題。大型系統通常有明確嘅 RE 階段，產出 requirements document（L4 用傳統觀點）。

易錯

Requirement 講 WHAT，唔講 HOW（設計）。

2. User requirements vs system requirements

一句講完

User requirements：寫俾客／用戶睇嘅高層次陳述（自然語言、user story），講用戶想達成咩。System requirements：寫俾開發者、tester 睇嘅詳細精確描述，要可量度、可測試。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解要兩種

唔同持份者需要唔同層次嘅資訊：客要確認方向啱，開發者要知道點樣做先算完成。System requirement 係將 user requirement 細化成可以起嘅 spec。

圖解：由 user 細化到 system
方面User requirementsSystem requirements
讀者客、用戶、product owner開發者、architect、tester、PM
語言自然語言、user story、簡單圖結構化自然語言、formal model、表格
細節抽象、一般、通常非正式詳細、具體、技術
可驗證性通常難直接 test，可能模糊應該精確、可量度、可 test
例子 2：to-do app

User：用戶可以標記 task 完成。System：系統應容許用戶揀 task 改 status 做「complete」；task 顯示剔號、移去「Completed」list；改動即時儲存。

易錯

「User requirement 唔使可以驗證」唔準確：佢通常難直接 test，但 Asm1 Q3 都要求寫可驗證嘅 user requirement（「Make sure requirements are verifiable」）。

3. Functional vs non-functional requirements

一句講完

FR：系統應提供嘅服務（亦可以講系統唔應該做咩）。NFR：對服務或功能嘅限制（performance、reliability、security…），通常適用於成個系統。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解 NFR 可能更重要

NFR 唔達標，成個系統可能冇用（例如飛機控制系統唔夠可靠就唔可以用）。NFR 影響整體 architecture 多過個別 component，而且一條 NFR 可能衍生其他 FR／NFR。

圖解 例子：2025 Q22(1) PowerPoint
  1. FR：「The application shall allow the user to insert an image from a local file into the current slide.」
  2. NFR（reliability）：「The application shall not lose more than 1 minute of the user's edits when it crashes, by auto-saving at least once every 60 seconds.」或者「MTBF ≥ 500 hours of use」。
易錯

NFR 冇數字 = 驗證唔到（「should be reliable」唔得分）。FR 都要具體：講清楚觸發條件同結果。

4. 可驗證嘅 NFR：metrics

一句講完

Verifiable NFR 係用某種可以客觀測試嘅量度寫出嚟嘅 NFR。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
點解難

客好難將目標變成可量度嘅 requirement：有啲目標冇簡單 metric（例如 maintainability）；metric 同日常體驗嘅關係唔清楚；驗證成本可能太高。

圖解：由模糊到可驗證
類別典型 metric
Performance95th percentile response ≤ 2 s；throughput ≥ 1,000 req/s
Availability99.9% uptime（≈ 8.76 小時停機／年）；99.99%（≈ 52.6 分鐘／年）
ReliabilityMTBF ≥ 1,000 小時；failure rate < 0.1%
Capacity最多 50,000 records；10,000 concurrent sessions
SecurityTLS 1.3、AES-256、MFA；5 次錯登入鎖戶口
Usability完成率 ≥ 90%；error rate < 5%；SUS ≥ 80
AccessibilityWCAG 2.2 AA；contrast ≥ 4.5:1
Compliance／SafetyPCI DSS、HIPAA；hazard rate < 10⁻⁹／小時
例子：availability 計數

99.9% uptime：一年停機時間 = \( (1-0.999) \times 365 \times 24 = 8.76 \) 小時。Asm1 Q3 官方例子：「Users shall be able to access the application for at least 99.5% of requests during their typical 9 AM–6 PM working hours, measured monthly.」

易錯

Availability（用唔用到）同 reliability（幾耐壞一次）唔同。寫 availability 要講量度期間（monthly／yearly）。

點解 NFR 難寫（L4 Challenges）
  • 客戶好難將目標轉成可量度嘅 requirement：有啲目標冇簡單 metric（例如 maintainability）；metric 同日常經驗嘅關係唔清楚；驗證成本可能太高。
  • Requirements document 入面好難將 F 同 NF 分開。
  • L4 例子 High-Frequency Trading：Performance「99.99% 嘅 trade 要喺收到 market signal 後 100 microseconds 內執行」；Availability「交易時段（9:30–16:00）要有 99.999%（five nines）uptime」。兩句都可驗證，因為有數字同條件。

5. F/NF 嘅界線唔清楚；NFR 之間嘅衝突

一句講完

Requirements 互相影響，F/NF 界線唔一定清楚：一條 NFR 可以衍生 FR；而唔同 NFR 之間可能互相衝突，要 trade-off。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
例子點解分唔清

Security 係 NFR，但「限制只有授權用戶可以存取」會衍生 FR：「系統要有 login、要驗證用戶身份」。睇抽象層次唔同，同一個需要可以寫成 NFR 或者一堆 FR。

圖解：performance vs maintainability（2023 Q22(2)） 例子：其他常見衝突
  • Security（多重驗證、加密）vs usability／performance。
  • Availability（多 server 冗餘）vs cost。
  • Safety（相關操作集中、少 component）vs performance。
易錯

「Requirement document 入面 F 同 NF 一定可以完全分開」係錯（L4：difficult to separate）。

6. RE process：elicitation、specification、validation（spiral）

一句講完

唔同機構嘅 RE process 差好遠，但都有 3 個 generic activities：elicitation（搵）、specification（寫）、validation（查）。實際上佢哋交錯重複，好似螺旋。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解係 spiral

寫低之後檢查，發現漏咗或者矛盾，又要返去問持份者；每轉一圈，requirement 由 business 層次細化到 user 層次再到 system 層次。

圖解：spiral 入面每個 activity 有咩（2025 Q22(2) 考歸類） 例子：2025 Q22(2) 答案
Activity歸類
i) system requirements modellingb) specification
ii) business requirements specificationb) specification
iii) feasibility studya) elicitation
iv) reviewc) validation
v) system requirements elicitationa) elicitation
vi) prototypingc) validation
易錯

Prototyping 喺 L4 同時係 elicitation 技術（core techniques）同 validation 技術；但喺 spiral 圖入面歸 validation，所以 2025 Q22(2) 答 validation 最穩陣，可以喺答案加一句說明。

7. Requirements elicitation：持份者同 4 個 stage

一句講完

Elicitation 係技術人員同持份者一齊了解 domain、工作流程、要嘅服務同功能。L4 嘅比喻：「Faster horse」問題（用戶講表面方案唔講根本問題）同 requirements iceberg（講出口嘅只係 10%）。

📑 Lecture 原 slide（4 張）＋逐張點睇（撳開）
持份者有邊啲
  • Primary users：每日真係用嘅人。
  • Secondary users：唔直接用，但提供資料或依賴佢（供應商、經理）。
  • Domain experts：識業務規則（價錢、法律、流程、例外）。
  • Regulatory bodies：政府同法律限制，冇得傾，成日被遺忘。
  • Opponents：反對個 project 嘅人。
圖解：elicitation 4 stage spiral
Stage目的（Asm1 官方）
Discovery & understanding同持份者互動，發現佢哋嘅 requirement（domain requirements 同文件都係來源）
Classification & organization將相關 requirement 分組成有條理嘅 cluster
Prioritization & negotiation排優先次序，解決 requirement 之間嘅衝突
Documentation將 requirement 記錄低（正式或非正式）
例子：elicitation 嘅挑戰（L4 五點）
  1. 持份者唔知自己真正想要咩。
  2. 佢哋用自己嘅術語、帶住隱含知識表達。
  3. 唔同持份者用唔同方式表達唔同 requirement。
  4. 機構同政治因素影響 requirement。
  5. 分析期間 requirement 會變：新持份者出現、商業環境改變。
易錯

「Classification」唔係「prioritization」：前者係分組，後者係排先後同解決衝突。

Elicitation 嘅困難（L4 Challenges，易出 T/F／短答）
  1. 持份者唔知自己真正想要咩。
  2. 持份者用自己嘅術語表達，帶住對自己工作嘅隱含知識。
  3. 唔同持份者有唔同 requirement，表達方式又唔同。
  4. 組織同政治因素可能影響 requirement。
  5. 分析期間 requirement 會變：新持份者出現、商業環境改變。

8. Elicitation 技術：interview、observation 等

一句講完

L4 嘅工具箱：interviews、observation（ethnography）、surveys、prototyping、brainstorming、document analysis。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
Interview 點做先啱

Open interview：冇固定稿、問開放式問題，用嚟探索；closed interview：預先定好封閉式問題。大部分 requirement 訪問兩樣混合：開放式探索、封閉式確認。

圖解：interview vs observation 例子：2024 Q22(1) Tom 錯喺邊
  1. Tom 只用一張是非題清單（純 closed interview）。
  2. 結果：受訪者冇機會講自己嘅工作、問題同隱含需要，Tom 只能確認自己已經諗到嘅嘢（iceberg 水面以下全部漏咗），亦冇得追問。
  3. 正確做法：混合開放式問題（探索，例如「你一日點樣處理入院登記？」）同封閉式問題（確認），根據回答追問。
易錯

Observation 嘅缺點「participants might change their way of working」同「knowledge-based activities are hard to observe」最常考。

9. Requirements specification：自然語言嘅問題同寫法指引

一句講完

Specification 係將 user 同 system requirements 寫入 requirements document。寫法：natural language、structured natural language、graphical notations（例如 use case）、mathematical specifications。

📑 Lecture 原 slide（5 張）＋逐張點睇（撳開）
自然語言嘅問題
類別問題
意思同理解模糊、唔精確、靠上下文、隱含、行內術語
邏輯同一致唔完整、互相矛盾、範圍／時間模糊、混淆 shall／may
規格同驗證冇正式結構、驗證唔到、F 同 NF 混埋
人同機構政治原因隱藏或淡化真正需要
文件維護冗長重複，難讀難改
圖解：L4 指引 例子：Asm1 Q3 官方答案

FR：「Users shall be able to create a new UML diagram from scratch, choosing from at least the most common UML types (e.g., Class, Sequence, Use Case).」

Structured natural language：用標準模板（function、description、inputs、source、outputs、action、pre／post-condition…），保留自然語言易明，但減少模糊。Use case：結構化描述 actor 點同系統互動達成目標。

易錯

「should」唔係「shall」：考試要求必須功能就用 shall。

10. SRS 結構；requirement vs design

一句講完

SRS（software requirements specification）係開發者應該實作咩嘅官方陳述，包括 user 同 system requirements；有標準（IEEE 830-1998、ISO/IEC/IEEE 29148）。佢唔係設計文件：講 WHAT 唔講 HOW。

📑 Lecture 原 slide（4 張）＋逐張點睇（撳開）
點解要標準結構

令客同開發者都用得：客睇前面嘅 introduction、user requirements；開發者睇 system requirements、models。

圖解：SRS 章節 例子：requirement 同 design 分唔開
  1. 要有初步 architecture 先組織得到 spec。
  2. 同現有系統互通會限制設計，同時帶出新 requirement。
  3. 某啲 NFR（例如用 N-version programming 做 reliability）會強制某種 architecture。
易錯

SRS 入面有 design 元素係可以接受，條件係 explicit、justified、traceable；偷偷塞入去先係 defect。

11. Requirements validation：5 個 check 同技術

一句講完

Validation 檢查 requirements 係咪定義咗客真正想要嘅系統，同 elicitation、analysis 有重疊。發現 requirement 錯好緊要：交付後先改，成本好高。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
5 個 check（2024 Q22(3) 考 4 個）
Check問題失敗例子
Validity反映唔反映用戶真正需要？做咗客唔需要嘅報表功能
Consistency有冇 requirement 互相矛盾？「資料只存喺手機」vs「任何裝置都睇到歷史」
Completeness客要嘅功能齊唔齊？有借書冇還書
Realism現有預算同技術做唔做到？3 個月內用 2 個人做全港即時交通 AI
Verifiability可唔可以驗證？「系統要好用」
圖解：3 種技術 例子：2024 Q22(3) 參考答案

a) Consistency：requirements 之間冇矛盾或衝突。b) Verifiability：每條 requirement 都可以用 test 或其他方法客觀檢查係咪達到。c) Realism：喺現有預算、時間同技術下做得到。d) Completeness：客要求嘅所有功能同限制都已經包括。

易錯

Requirements validation（檢查 requirement 本身）同 software validation testing（檢查完成咗嘅軟件）唔同。

12. 管理 requirement 改變：traceability matrix 同 moving target

一句講完

Requirements traceability matrix 係一個表，將每條 requirement 連去來源、設計、code、test case 同其他 requirement。Backward：requirement 由邊度嚟；forward：requirement 去咗邊。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解要
  • Static correctness：證明系統完整、正確、有驗證、合規。
  • Dynamic resilience：支援 impact analysis、change propagation、scope control、進度追蹤。
圖解 例子：moving target（2025 Q22(4)）

Moving target：開發期間 requirement 不斷改變，系統要追住一個郁緊嘅目標，而且冇根治方法（L2）。兩個通用方法：change anticipation（例如用 prototype 預早發現要改咩）同 change tolerance（例如 incremental development，令改動只影響未做嘅 increment，成本低）。

易錯

Moving target 冇 solution，只可以減低改變成本；答「凍結 requirement 就解決到」會失分。

三、完整示範：2022 Q22 = Asm1 Q4（Tom 圖書館，12 分）

📄 原卷題目截圖：2022 Q22 · Requirements（12 分）（撳開）
一分鐘重點
  • 先背 4 個 stage 名 → 每個 stage 一句目的 → 喺情境搵對應嘅錯。官方 solution 有，以下跟住寫。

A large local public library with 20 librarians and 30 other staff members recently outsourced the development of a new computer-based book management system… Tom randomly picked 5 librarians and 5 frequent users of the library and had an interview with each of them. In each interview, Tom asked preselected questions and had open discussions with the interviewee, but he waited until all the interviews were completed to write down all the information he gathered from the interviews. Afterward, he compiled a long, flat list of requirements from the information, and the company started making plans based on those requirements.

Step 1：情境逐句對 stage

Step 2：答案

(1) 四個 stage（0.5 分 × 4）Requirements discovery and understanding; requirements classification and organization; requirements prioritization and negotiation; requirements documentation.
(2) 目的（<100 words）Discovery and understanding: interact with stakeholders to discover their requirements. Classification and organization: group related requirements into coherent clusters. Prioritization and negotiation: prioritize requirements and resolve requirement conflicts. Documentation: document the requirements as input to the next round of the spiral.
(3) 每個 stage 嘅問題（<100 words）Discovery: too few stakeholders were involved; other staff, managers and less frequent users were not interviewed, so requirements may be missing. Classification: the requirements were compiled into a long, flat list without being grouped into coherent clusters. Prioritization and negotiation: no prioritization was done, and conflicts between stakeholders were not negotiated, especially as only a few people were consulted. Documentation: information was written down only after all interviews, so details may have been forgotten or recorded inaccurately.

考試見到「Tom」就諗 elicitation 4 stage：discovery 揾邊個問、classification 有冇分組、prioritization 有冇排先後同傾掂衝突、documentation 有冇即時記。

(1) Explain the differences between FR and NFR. Give one FR and one reliability NFR for a desktop presentation application. (<100 words, 4 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • FR：系統提供嘅 service（做咩）
  • NFR：對 service 嘅 constraint（performance、reliability），通常成個系統
  • FR 例：insert image into slide
  • NFR 例（reliability）：每 60 秒自動儲存，crash 最多失 1 分鐘
答案Functional requirements state the services the system should provide, i.e., what it should do in particular situations. Non-functional requirements are constraints on those services, such as performance or reliability, and often apply to the system as a whole. FR: The application shall allow the user to insert an image from a local file into the current slide. NFR (reliability): The application shall automatically save the open presentation at least every 60 seconds, so that no more than 1 minute of edits is lost when it crashes.

(2) Map activities to a) elicitation b) specification c) validation. (3 points)

參考答案
答案i) b　ii) b　iii) a　iv) c　v) a　vi) c

出處：L4 spiral view。Prototyping 同時係 elicitation 技術，但 spiral 圖將佢放喺 validation。

(3) Sort the four elicitation stages. (2 points)

參考答案
答案c) discovery and understanding → a) classification and organization → b) prioritization and negotiation → d) documentation

(4) Explain the moving target problem and the two general approaches to cope with it. (<100 words, 3 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Moving target：開發期間 requirement 一直變，冇辦法消除
  • 方法 ① Change anticipation（prototype）
  • 方法 ② Change tolerance（incremental development）
答案The moving target problem is that requirements keep changing while the system is being developed, so developers are aiming at a target that moves; it cannot be eliminated. Change anticipation: include activities that foresee changes before significant rework is required, e.g., developing a prototype to show key features to customers early. Change tolerance: design the process so that changes can be accommodated at low cost, e.g., incremental development, where changes affect only increments not yet implemented.

(1) Tom interviewed hospital users with only a list of true/false questions. What did he do wrong and how should interviews be conducted? (<60 words, 2 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • 錯：只用 closed true/false 問題 → 受訪者講唔到工作、問題、隱含需要；冇得追問
  • 正確：open（探索）+ closed（確認）混合，有意外答案就 follow-up
答案Tom used only closed true/false questions, so interviewees could not describe their work, problems and implicit needs, and he could not follow up. Interviews should mix open-ended questions to explore the domain and closed questions to confirm details, with follow-up questions when answers are unexpected.

(2) How to gather requirements via observation; one advantage and one disadvantage. (<100 words, 4 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • 做法：analyst 喺自然環境睇用戶真實工作，唔打擾
  • 優點：用戶唔使解釋；見到社會同組織因素
  • 缺點：被觀察會改變做法；知識型工作睇唔到
答案In observation (ethnography), an analyst watches users doing their real work in their natural environment without interrupting, recording how tasks are actually carried out. Advantage: people do not have to explain or articulate their work, and the observer gains practical insight, including social and organizational factors. Disadvantage: participants may change the way they work while being observed, so the observer may not get a true picture; also, knowledge-based activities are hard to observe.

(3) Explain consistency, verifiability, realism and completeness. (<100 words, 6 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • a) Consistency：冇互相矛盾
  • b) Verifiability：可以客觀測試
  • c) Realism：預算、時間、技術做得到
  • d) Completeness：客戶要嘅功能齊
答案a) Consistency: the requirements do not conflict with or contradict each other. b) Verifiability: each requirement can be objectively checked, e.g., by a test, to decide whether the delivered system meets it. c) Realism: the requirements can be implemented within the available budget, schedule and technology. d) Completeness: the requirements include all the functions and constraints intended by the customer.

1) Use an example to explain why the distinction between FR and NFR is not clear-cut. (<100 words, 3 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Requirement 唔獨立，一條會衍生其他
  • 例：NFR「只有授權員工睇病人記錄」（security）
  • → 衍生 FR：「要有 login」、「顯示前 check role」
  • 寫成 constraint 定 service 視乎詳細程度
答案Requirements are not independent, and one requirement often generates others. For example, a security requirement "Only authorized staff shall access patient records" is non-functional, constraining the whole system. However, to satisfy it, functional requirements must be added, such as "The system shall provide a login function that authenticates users" and "The system shall check a user's role before displaying a record." Whether this need is written as a constraint or as services depends on the level of detail.

2) Why do high performance and high maintainability conflict in a distributed system? (<100 words, 3 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Performance 要：少數大 component、放同一部機、少網絡溝通
  • Maintainability 要：好多細、獨立 component、清楚 interface
  • 分佈式系統：細 component → 多遠端溝通 → 慢；大 component → 難改 → 衝突
答案High performance requires localizing critical operations in a few large components deployed on the same machine to minimize communication over the network. High maintainability requires using fine-grained, self-contained components with clear interfaces and layers so they can be easily changed or replaced. In a distributed system, more fine-grained components mean more remote communication and indirection, which reduces performance, while fewer large components make changes harder.

3) For a desktop word processor, define one requirement verifiable via inspection and one via testing. (<100 words, 4 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Inspection 例：source code 符合 Java coding standard、每個 public method 有註解
  • Testing 例：100 頁文件 2 秒內開到
答案Inspection: "All source code of the application shall conform to the company's Java coding standard, and every public method shall have a documentation comment." (checked by reviewing the code). Testing: "The application shall open a 100-page document within 2 seconds on the reference PC." (checked by executing the application and measuring the time).

八、短答題

1. Distinguish user requirements and system requirements, with one example each. (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • User req：高層次、自然語言、俾客戶睇（「可以搜尋產品」）
  • System req：詳細、精確、俾開發者（搜尋 name／category／price，10,000 件 2 秒內）
答案User requirements are high-level, natural-language statements for customers and users describing what they need, e.g., "A customer should be able to search for products." System requirements are detailed, precise descriptions for developers and testers of the services and constraints, e.g., "The system shall allow searching by name, category and price range and return results within 2 seconds for up to 10,000 products."

2. Name four stakeholder types and give one challenge of requirements elicitation. (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • 持份者：primary users、secondary users、domain experts、regulatory bodies
  • 困難：持份者唔知自己想要咩，用自己術語 + 隱含知識 → analyst 易誤解
答案Primary users who use the system daily; secondary users who feed or depend on it, such as managers; domain experts who know the business rules; and regulatory bodies that impose legal constraints. Challenge: stakeholders often do not know what they really want and express requirements in their own terms with implicit knowledge, so analysts may misunderstand them.

3. Why are requirements and design inseparable in practice? (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • ① 要有初步 architecture 先組織到 spec
  • ② 同現有系統互通 → 限制設計、帶出新 requirement
  • ③ 某啲 NFR 強制某種 architecture（N-version programming）
  • Design 元素可以有，但要 explicit、justified、traceable
答案An initial architecture is often needed to structure the requirements specification; interoperability with existing systems constrains the design and imposes new requirements; and some non-functional requirements, such as reliability achieved through N-version programming, force a particular architecture. Design elements in a specification are acceptable if they are explicit, justified and traceable.

九、常見疑問

Q：寫 requirement 要唔要加 rationale？
L4 指引建議加，Asm1 注意事項都講「Provide an explanation in parentheses if necessary」。字數夠就加一句。
Q：Prototyping 係 elicitation 定 validation？
兩樣都係。L4 core techniques 將佢列做 elicitation 技術；validation techniques 亦有佢；spiral 圖放喺 validation。2025 Q22(2) 答 validation，可以加一句說明。
Q：Availability 同 reliability 點分？
Availability：需要時用唔用到（uptime %）；reliability：幾耐壞一次（MTBF、failure rate）。
Q：Validity check 同 completeness check 有咩分別？
Validity 問「寫咗嘅係唔係真正需要」（有冇寫錯或寫多咗）；completeness 問「需要嘅有冇寫晒」（有冇漏）。
Q：Moving target 係 L2 定 L4？
L2 coping with change。2025 放喺 RE 題（Q22(4)），兩課都要識。
