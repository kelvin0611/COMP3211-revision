二、筆記：由零講起

一分鐘重點
  • Evolution 由 change proposals 推動；CCB 評估成本效益再批准。Evolution 同新開發最大分別：要先理解現有程式。
  • Legacy：低質低值 scrap；低質高值 re-engineer／replace；高質低值 scrap 或 maintain；高質高值 maintain。
  • VC：codeline、baseline、check-out／check-in、branch、merge；distributed 每個 workspace 係 full clone。
  • Reuse：framework（skeleton）、product line（一家人）、component（自己包一份，provides／requires interface）、service（引用外部）、MDE（由 model 生成 code）。

1. Evolution process 同 change requests

一句講完

Change proposals 係系統演化嘅推動力；演化係一個循環：impact analysis → release planning → change implementation → system release。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
Change request 嘅 4 個來源（2025 Q27(1)）
  1. 持份者嘅 bug reports。
  2. 新 requirement 嘅要求。
  3. 開發團隊嘅改善想法。
  4. 要求適應新環境（新 OS、新硬件）。
圖解：general model 例子：evolution 同新開發嘅關鍵分別

Change implementation 都係 iterative 嘅 design、implement、test，亦要更新 requirement 同 design 文件；但同新開發唔同，evolution 第一步係理解現有程式（佢點樣結構、點樣實現功能、改動會影響邊度）。

易錯

具體 evolution process 取決於：維護緊嘅軟件類型、用嘅開發 process、參與者嘅技能經驗。

2. Change management 同 Change Control Board（CCB）

一句講完

Change management：分析 change 嘅成本同效益，批准有成本效益嘅 change，追蹤邊啲 component 改咗。決定權喺 CCB。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解要

Change request 好多，唔可以個個即刻做：要先檢查有效性、分析影響同成本，再由 CCB 按優先揀，避免亂改同浪費。

圖解：完整流程（2024 Q26 填圖） 例子：一張 CR 嘅一生
  1. 用戶提交「匯出 PDF 時中文亂碼」。
  2. Customer support 檢查：有效 → register（無效就 close）。
  3. 開發團隊做 implementation analysis（要改邊度）同 cost/impact analysis（幾多工、影響咩）。
  4. CCB assess，再 select 今次做唔做；唔做就 close。
  5. 做嘅話 modify software → test；fail 就再改，pass 就 close CR。
易錯

Cost/impact analysis 係開發團隊做，結果交俾 CCB 評估；CCB 唔係寫 code 嘅人。

3. Agile 同 evolution；maintenance 嘅成本

一句講完

Agile 本身係 incremental，所以 evolution 只係開發 process 嘅延續。Maintenance 成本通常高過開發成本。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解 maintenance 咁貴（L10 四點）
  1. 舊 code 越嚟越難改。
  2. 開發同維護分開，冇誘因寫易維護嘅 code。
  3. 維護通常交俾經驗少、domain 知識有限嘅員工。
  4. 新團隊要花大量時間理解 legacy 系統。
圖解：交接問題 例子：agile evolution practices

頻繁 release；自動化 regression testing（改動時好有價值）；將 change 寫成新嘅 user story。

易錯

Maintenance 側重漸進改動（改現有 component 或加新 component），唔係大改 architecture。

4. Technical debt

一句講完

Technical debt：今日揀咗快而易嘅做法，代替一個要耐啲嘅好做法，將來要付嘅隱藏成本。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
金融比喻
  • Principal（本金）：最初寫嘅 shortcut code。
  • Interest（利息）：之後開發變慢、bug 變多。
  • Bankruptcy（破產）：系統冇得再維護。
圖解：Technical Debt Quadrant 例子

為咗趕 demo，PIM 項目將所有 command 寫晒喺一個 2000 行嘅 if-else（deliberate + prudent，如果之後有計劃 refactor）。之後每加一個 command 都要改呢個大 function（利息）；最後冇人敢郁（破產）。

易錯

Technical debt 唔係「bug」：佢係設計／實作上嘅捷徑，令將來改動更貴。

5. Legacy systems：定義、點解貴改、點解難換

一句講完

Legacy system：依賴過時語言同技術（新開發已經唔用）嘅舊系統；佢唔止係軟件，仲包括硬件、library、同埋嵌入咗嘅業務流程。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
貴改 vs 難換
貴改（expensive to change）難換（risky to replace）
Code decay：結構退化、風格唔一致、複雜優化Knowledge gap：冇 spec、業務規則冇記錄
Knowledge gap：文件差、語言過時、識嘅人越嚟越少Business entanglement：同核心流程綁死
Data impact：資料有錯、重複、唔一致Project risk：好大機會延誤、超支
圖解：legacy 唔止係 code 例子：3 個策略方向
  1. 繼續維護（照舊，或者先 re-engineer）。
  2. 用新系統取代。
  3. 完全棄用，改變業務流程令佢唔再需要。
易錯

Knowledge gap 喺「貴改」同「難換」兩邊都出現；2025 Q27(2) 要嘅係貴改嘅 3 個：code decay、knowledge gap、data impact。

6. 揀 evolving strategy：business value × system quality

一句講完

策略取決於兩個評估因素：business value 同 system quality，畫成四格。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點評估
  • Business value：訪問持份者：系統點用、支援咩業務流程、output 有咩用。
  • System quality：評估易明度、文件、資料、performance、語言、configuration management、test data；量度 change request 數量、user interface 數、資料量。
圖解：四格 例子

銀行 25 年嘅 COBOL 核心系統：每日都要用（高值），但冇文件、得兩個人識（低質）→ re-engineer，或者有合適現成系統就 replace。

易錯

高質低值唔係「一定 scrap」：如果維護成本低，可以繼續用。

7. Re-engineering vs refactoring

一句講完

Re-engineering：重組或重寫 legacy 系統（部分或全部），唔改功能，令佢易維護。Refactoring：開發同演化期間持續改善程式，唔加功能，屬「預防性維護」。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
Re-engineering 點解好過 replacement

風險低、成本低。適用於部分（唔係全部）sub-system 需要頻繁維護嘅情況。

圖解：時間軸 例子：re-engineering 成本因素同限制
  • 成本因素：原本軟件嘅質素、工具支援、要轉換幾多資料、有冇專家。
  • 限制：冇可能轉換 programming paradigm（例如 procedural 變 OO）；大改 architecture 或資料管理好貴；結果唔會好似重新寫咁易維護。
易錯

Re-engineering 唔係「加新功能」；加功能係一般 maintenance／evolution。

8. Version management：codeline、baseline、check-out／check-in

一句講完

Version management 追蹤 software component 同用佢哋嘅系統嘅唔同版本。兩個目標：管理 codeline 同 baseline；確保唔同開發者嘅改動唔會互相干擾。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
術語
  • Codeline：一連串 source code 版本（V1.0 → V1.1 → V1.2）。
  • Baseline：一個 release 用嘅確切 component 版本、library、config 檔嘅 snapshot。
  • Private workspace：開發者改嘢唔影響其他人嘅地方。
圖解 例子：branching 同 merging

Branching：開出獨立嘅版本序列（做新功能、修 bug、試驗、隔離環境）。Merging：將分支合返，產生包含所有改動嘅新版本；分支分得越遠、衝突越多，merge 越難。

易錯

Codeline 係「一條版本序列」；baseline 係「某個 release 嘅完整組合 snapshot」。

9. Centralized vs distributed version control

一句講完

Centralized（SVN、CVS）：只有一個 master repository，workspace 只有 check-out 咗嘅 component，冇完整歷史。Distributed（Git、Mercurial）：多個 repository 同時存在，每個 workspace 係完整 clone（包括全部歷史）。

📑 Lecture 原 slide（5 張）＋逐張點睇（撳開）
比較（Asm2 Q4、2022／2024 必考）
CentralizedDistributed
Repository 數量1 個 master每個開發者都有一個完整 repository
Workspace 內容只有 check-out 咗嘅 component成個 project + 全部歷史
優點易學易設定；部分下載快Backup；offline 工作；快；branching 平；merge 衝突少
Storage存 delta，要套一連串改動先重建檔案壓縮完整檔案，讀取快
Branch實體複製成個目錄：貴 →「branch-phobia」只係指向 commit 嘅 pointer：幾乎冇成本 →「branch-heavy」
Merge喺中央 server 做，歷史線性、ancestry 唔完整，衝突壓力持續任何 clone 都可以 merge；歷史係 DAG，搵到準確 common ancestor（three-way merge）

易錯

Centralized 都有優點（易學、部分下載快），唔好寫「centralized 冇優點」。

12. Application frameworks 同 software product lines

一句講完

Framework：一組協作嘅 class／object／component，提供一類應用嘅可重用 skeleton architecture（例如 Java Swing、Spring）。Product line：一家相關應用共用一個 architecture 同一套 reusable component，每個版本按唔同 requirement 特化（例如 printer driver、MS Office）。

📑 Lecture 原 slide（7 張）＋逐張點睇（撳開）
點樣擴展 framework
  1. Inheritance（white-box）：加 concrete class 繼承 framework 嘅 abstract class，override operation（例如 extends JFrame）。
  2. Callbacks（black-box）：加 method，framework 偵測到 event 時 call 返佢（例如 ActionListener 嘅 actionPerformed）。Framework 控制整體流程，「call back」你嘅 code。
圖解：printer driver product line 例子：framework vs product line
FrameworkProduct line
目的幫你整一類應用幫你整一家相關應用
OO依賴 OO（inheritance、polymorphism）唔一定
範圍通用包含 domain／platform 資訊
用途軟件導向常用嚟控制設備
擁有者可以係第三方通常一間機構
易錯

Framework 缺點：複雜，學習曲線好斜。

13. Component-based software engineering（CBSE）

一句講完

CBSE 以重用 component 為基礎：component 係由 interface 定義嘅獨立可執行單元，比 object class 更抽象，可以做獨立 service provider。

📑 Lecture 原 slide（5 張）＋逐張點睇（撳開）
Component 5 個特徵 + 2 個 interface
  • Composable、Deployable、Documented、Independent、Standardized。
  • Provides interface：佢提供嘅 service；requires interface：佢運作需要其他 component 提供嘅 service。
  • Component model（EJB、COM+／.NET、CCM）定義 interface、usage information、deployment 嘅標準。
圖解：component 喺 container 入面 例子：兩種 CBSE process

Development for reuse：開發俾其他應用重用嘅 component／service。Development with reuse：用現有 component／service 組合新應用。

易錯

Support services（application-independent，例如 transaction、security）同 platform services（令 component 喺分散環境溝通）係兩類。Container 嘅 service 點解必要：唔使每個 component 重複實作，令 component 專注業務邏輯，而且由 container 統一管理（例如 transaction 一致 commit／rollback）。

14. Service-oriented SE 同 model-driven engineering

一句講完

Service-oriented SE 用 web service（鬆耦合、封裝獨立功能、可以分散、程式存取）建分散式應用；應用引用外部 service，唔會自己包一份。MDE：model 係主要產出，程式由 model 自動生成。

📑 Lecture 原 slide（6 張）＋逐張點睇（撳開）
SOA 角色同好處
  • Service provider：設計、實作、定義 interface，發佈資訊去 registry。
  • Service requestor：搵 service spec、定位 provider、bind 同用標準 protocol 溝通。
  • 好處：任何 provider 都可以提供；可以延遲 binding 到部署或執行時；可以組合現有 service 建新 service；按實際用量付費；應用更細（適合手機）。
圖解：SOA 三角 + MDA 模型 例子：component vs service（2023 Q26(1)）
方面ComponentService
Interface 規格Provides／requires interface，跟特定 component model（EJB、.NET）按標準、platform-independent 嘅 service description，發佈喺 registry
溝通部署喺 container，經 container／middleware（method call）用標準 protocol（HTTP／HTTPS）同標準資料格式（XML）傳 message
多個系統使用每個應用包含自己一份 component copy應用引用同一個外部 service，可以跨機構共用
易錯

MDE 採用有限：工具支援少；討論用嘅 model 唔一定啱用嚟實作；複雜系統嘅難題通常唔係 implementation；platform independence 只對大型長命系統重要；agile 興起分散咗注意力。

(1) Identify three reasons for change requests and one critical difference between initial development and change implementation. (5 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）

答案Reasons: 1) bug reports from system stakeholders; 2) requests for new requirements; 3) requests to adapt the system to new environments (also: improvement ideas from the development team).   • 2 個評估因素：business value（訪問持份者）+ system quality（易明、文件、change request 數量）
答案A legacy system is an older system that relies on outdated languages and technologies no longer used for new development, including its hardware, software, libraries and embedded business processes. It is expensive to change because of 1) code decay: degraded structure and inconsistent styles; 2) a knowledge gap: poor documentation, obsolete languages and few skilled staff; 3) data problems: errors, duplication and inconsistency. The strategy depends on the system's business value, assessed by interviewing stakeholders, and its system quality, assessed from factors such as understandability, documentation and change-request volume.

(1) Explain two advantages of DVCS: a) backup mechanism b) supports development of several projects sharing components, by default. (<100 words, 4 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • a) Backup：每部機完整 clone → 任何一份都還原到
  • b) Project support：clone 成個 project 連所有 component → 本機 build／test；唔同 project 共用 component repo
答案a) Every developer's machine holds a complete clone of the project repository, including all versions and history, so each clone acts as a backup; if the shared repository fails, it can be restored from any clone. b) Project support is the default way of working: developers clone the whole project with all its components rather than checking out individual files, so they can build and test the entire system locally, and different projects can clone and share the same component repositories.

(2) Describe how DVCS supports open-source development where people work simultaneously without central coordination. (<150 words, 6 points)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • 流程：Fork → Clone → Branch → Commit（可離線）→ Push 去自己 fork → Pull Request
  • Maintainer review → merge
  • 保持更新：fetch + merge upstream
  • 結果：好多人平行工作，唔使寫入權限、唔使中央協調
答案In DVCS, anyone can fork the definitive project repository and clone it to their own machine, obtaining a full copy with the entire history. Contributors do not need write permission or permission to start: they create a feature branch locally, make and commit changes independently, and even work offline. When ready, they push the changes to their own public fork and open a pull request. The project maintainer reviews the request and decides whether to merge it into the definitive repository. Because every merge commit records all parents, merges are accurate and limited to the actual feature changes. Contributors keep their forks up to date by fetching and merging upstream changes. Thus many people can work in parallel, and coordination happens only when the maintainer chooses which contributions to pull.

八、短答題

1. Distinguish refactoring and re-engineering. (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Refactoring：開發期間持續改善結構、唔加功能、預防性維護
  • Re-engineering：legacy 系統維護成本上升之後，重組／重寫成易維護嘅新系統、唔改功能
答案Refactoring is a continuous process of improving program structure throughout development and evolution without adding functionality; it is preventative maintenance that avoids code degradation. Re-engineering transforms a legacy system, after it has been maintained for some time and maintenance costs are rising, into a new, more maintainable system; it restructures or rewrites parts of the system without changing its functionality.

2. What is technical debt? Explain the financial analogy. (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Technical debt：而家揀快捷方法，將來要俾嘅代價
  • Principal = 捷徑 code；Interest = 開發變慢、bug 多；Bankruptcy = 維護唔到
  • Refactoring = 還本金
答案Technical debt is the implied future cost of choosing an easy, quick solution now instead of a better approach that would take longer. The principal is the shortcut code; the interest is slower future development and more bugs; bankruptcy is when the system becomes unmaintainable. Refactoring pays off the principal before interest compounds.

3. Distinguish application frameworks and software product lines. (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）
  • Framework：一「類」應用嘅骨架；靠 OO inheritance + callback；通用；可以第三方
  • Product line：一「系列」相關應用，共用 architecture + component；嵌入 domain／平台資訊；常見於控制設備；通常一間機構擁有
答案A framework provides a reusable skeleton architecture for a type of application and relies on object-oriented inheritance and callbacks; it is general and may be provided by a third party. A product line is a family of related applications sharing a common architecture and reusable components, each specialized for different requirements; it embeds domain or platform information, is often used for equipment control software and is usually owned by one organization.
