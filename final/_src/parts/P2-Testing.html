Partition testing 表答題步驟（必識）

  1. 標出每個 if／loop 條件嘅行號：表頭 C1、C4… 就係呢啲行。
  2. 由第一個條件開始畫決策樹：每個條件分 T／F；遇到 return／throw 就停（後面嘅條件填 --）。
  3. 刪走做唔到嘅葉：例如「amount ≤ 100」同「amount > 500」唔可能同時成立。
  4. Loop 條件：記錄成個 test 入面出現過嘅值集合，例如 true,false；loop 一次都冇行就係 false。
  5. 每片葉揀一個具體 input，用 code 逐行行一次計 expected result。
  6. 寫表：每行 input、expected、每個 C 欄（T／F／T,F／--）。行數 = 做得到嘅葉數。

二、筆記：由零講起

一分鐘重點
  • Testing 兩個目標：validation testing（證明符合 requirement）同 defect testing（搵 bug）。Testing 只能證明有錯，唔能證明冇錯。
  • 三個 stage：development testing（unit → component → system）、release testing（獨立團隊）、user testing（alpha、beta、acceptance）。
  • Black-box 由 spec 出 test；white-box 睇 code，量 coverage（statement、branch、path）。
  • Partition testing：同一組 input 程式反應一樣，每組揀一個；加 boundary value analysis。

1. Testing 嘅兩個目標：validation testing vs defect testing

一句講完

Testing = 用 input 執行程式，檢查結果。目標一：證明軟件符合 requirement（validation testing）；目標二：搵出軟件行為錯嘅情況（defect testing）。

點解要分

兩種 test 對「成功」嘅定義相反，2025 Q26(1) 就係考呢點：

Validation testingDefect testing
Test case 點揀反映系統正常用法刻意揀古怪、容易出錯嘅 input
Successful test系統按預期運作令系統出錯、暴露 defect
例子Release testing、acceptance testingUnit testing、development 期間嘅 system testing
圖解：Input-output model 例子

測試 calculateDiscount：validation test 用「premium 會員買 $200」，期望 0.15，結果啱 = 成功。Defect test 用「amount = -0.0001」、「amount = 500.0（剛好 boundary）」專登撩 bug；如果令程式回錯數 = 呢個 test 成功（搵到 bug）。

易錯

Defect testing 嘅「successful」係搵到 bug，唔係「全部 pass」。另外「100% coverage = 冇 bug」係錯（coverage fallacy）。

2. Verification vs validation；static vs dynamic

一句講完

Verification：「Are we building the product right?」— 軟件啱唔啱 specification。Validation：「Are we building the right product?」— 軟件係唔係客真正想要嘅。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解要兩樣都做

Spec 本身可能寫錯：完全符合 spec（verification 過）但係客唔啱用（validation 唔過）。V&V 有兩種做法：

  • Static（唔使行 code）：inspection、walkthrough、static analysis，可以檢查 requirement、design、code 任何文件。
  • Dynamic（行 code）：testing。
圖解 例子：2023 Q25(1) testing vs inspection
Testing（dynamic）Inspection（static）
Testing 嘅優點可以檢查 non-functional emergent property（performance、usability）；檢查真實運行時 component 之間嘅互動；可以自動化、重複做（regression）—
Testing 嘅缺點一個錯可以遮住另一個錯（error masking）；要有可執行嘅 code，未完成嘅版本要寫 test harness；檢查唔到 maintainability、標準遵守呢類質素L9：可以用喺任何文件；唔使理錯誤之間嘅互相影響；可以考慮更廣嘅質素屬性
易錯

V&V 嘅 V 唔係同一樣嘢。考 T/F 成日將兩句問題調轉。Inspection 唔能取代 testing：佢檢查唔到 performance 呢類運行時屬性。

3. Testing 三個 stage

一句講完

Development testing（開發團隊做，分 unit → component → system）→ release testing（獨立團隊測完整版本）→ user testing（用戶參與）。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解要分層

越早搵到 bug 越平（L1：late fix 要改 code、改文件、再 test、做 regression）。細單位先測，組合後再測介面，最後測成個系統同真實環境。

圖解 例子：PIM 項目
  1. Unit：測 Task.isOverdue()。
  2. Component：測 model package 嘅 interface（search 同 update 一齊用）。
  3. System：用 command line 由頭到尾行一個 user story。
  4. Release：另一組同學淨係睇 SRS 出 test。
  5. User：俾真用戶喺自己部機試（beta）。
易錯

System testing 同 release testing 都測完整系統，但 system testing 由開發團隊做、目標係搵 bug（defect testing）；release testing 由獨立團隊做、目標係證明夠好（validation testing）。

4. Black-box vs white-box testing

一句講完

Black-box：唔睇 code，由 requirement／spec 出 test。White-box（structural）：用 code 內部結構出 test，量度 code coverage。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解兩樣都要

Black-box 檢查「應該做嘅有冇做」（包括漏咗嘅功能，white-box 睇唔到漏咗嘅 code）；white-box 檢查「寫咗嘅 code 有冇行過」（搵 dead code、未測嘅 branch）。

圖解 例子：2023 Q25(3)
  1. 本質分別：test 係咪由 code 內部結構推出嚟。
  2. 開發團隊做唔做到 black-box？做到。Black-box 只係話「設計 test 時唔用 code 知識」，邊個做都得（例如開發團隊嘅 system testing 用 requirement 出 test）。
  3. Black-box 用唔用到 coverage？用到。Coverage 係行 test 時用工具量度執行咗幾多 code，同 test 點設計無關；可以用嚟衡量 black-box test suite 嘅質素（例如發現冇 test 行過嘅 branch）。
易錯

「Black-box 一定要外人做」係錯；只係唔用內部知識。「White-box test 夠晒」都錯：漏咗冇寫嘅功能，coverage 都會係 100%。

5. Code coverage：statement、branch、path

一句講完

Coverage 量度 test suite 行過幾多 code：statement（每句行過最少一次）、branch（每個 if／loop 嘅 true 同 false 都出現過）、path（每條執行路線都行過）。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
$$\text{Statement coverage} = \frac{\text{executed}}{\text{all statements}}\times 100\%$$ $$\text{Branch coverage} = \frac{\text{outcomes exercised}}{\text{all outcomes}}\times 100\%$$ 點解 branch 比 statement 強

冇 else 嘅 if：一個令條件 true 嘅 test 已經行晒所有 statement，但 false 嗰邊從未試過。100% branch coverage 一定包含 100% statement coverage（假設冇死 code），反過來唔成立。Path coverage 再強，但 loop 令 path 數量爆炸。

圖解：2023 Q25(2) canFormTriangle 
1 boolean canFormTriangle(double x, double y, double z){
2   boolean result = false;
3   if (x > 0 && y > 0 && z > 0)
4     if (x + y > z && x + z > y && y + z > x)
5       result = true;
6   return result;
7 }
例子：答案（Java 跑過）
目標xyzreturn
100% statement345true
100% branch345true
123false
011false
易錯

Coverage fallacy（L9）：100% coverage 只代表 code 行過，唔代表 0 defects。(1,2,3) 係「兩邊和 = 第三邊」嘅 boundary，揀佢仲可以順便檢查 > 定 >=。

6. Equivalence partitioning + boundary value analysis

一句講完

將 input 分成等價類（partition）：同一組入面程式反應一樣，所以每組揀一個代表就夠；再喺 partition 嘅邊界加 test，因為 bug 最常喺邊界（off-by-one）。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解要咁做

窮舉所有 input 冇可能；隨便揀又會漏。Partition 保證每種行為都測到，BVA 補充最易錯嘅位置（例如用 < 代替 <=）。

圖解：有效範圍 1–100 例子：L9「接受 4–10 個五位數、而且 > 10,000」
  1. 數量 partition：少過 4（例如 3）、4–10（例如 7）、多過 10（例如 11）；邊界 3、4、10、11。
  2. 數值 partition：< 10000（例如 9999）、10000–99999（例如 50000）、> 99999（例如 100000）；邊界 9999、10000、99999、100000。
易錯

Partition 唔止 valid 嗰組，invalid 嘅 partition 都要測（例如負數、空 list）。L9 sequence 指引：測單一元素、長度 0、唔同長度，同埋第一、中間、最後一個元素。

7. 考試版 partition testing：用 branch coverage 分組

一句講完

真卷將「同一 partition」定義為「same branch coverage」：行過嘅 if／loop 一樣，而且每個條件取過嘅值（T、F 或 T,F）一樣。所以 partition 數 = 決策樹入面做得到嘅葉數。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解咁定義

咁樣分組係客觀、可以逐行驗證嘅：兩個 test 行同一條路、每個條件結果一樣，程式對佢哋嘅處理就一樣。

圖解：calculateDiscount（2025）決策樹 例子：數 class 嘅方法
  1. C1（amount < 0）：T → 即刻 throw，1 片葉。
  2. C1 F → C4（isPremium）：T 去 C5，F 去 C8。
  3. C5、C8 每個分 T／F，之後全部都會去 C10（第 10 行唔喺 if-else 入面），所以每條再分 T／F：2 × 2 × 2 = 8 片葉。
  4. 刪走做唔到嘅：premium + amount ≤ 100（C5 F）+ amount > 500（C10 T）矛盾 → 剩 7。
  5. 加返 C1 T：總共 8 個 test（Java 窮舉確認）。
易錯

冇行到嘅條件寫 --，唔好寫 F。例如 isPremium = true 時第 8 行 else if (isStudent) 根本冇 evaluate。Loop 條件要寫整個 test 期間出現過嘅值集合（通常係 true,false）。

8. Test case 有咩；幾時開始設計 system test

一句講完

一個 test case 要有：input data、test steps、test oracle（判斷 output 啱唔啱嘅機制／預期結果）。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解要 oracle

冇 oracle 就唔知 test pass 定 fail。Oracle 可以係 spec 寫嘅預期值、舊版本嘅結果、人手計嘅答案，或者一條規則（例如「output 一定排好序」）。

圖解：V-model（test 喺開發早期已經可以設計） 例子：2025 Q26(2)
  1. Test oracle：判斷 test 結果啱唔啱嘅依據，例如 spec 寫明 premium 買 $200 應該得 0.15。
  2. Waterfall 中 system-level test：requirements analysis and definition 完成之後就可以開始設計，因為 system test 由 requirement 推出嚟。
  3. Testing 驗證唔到嘅 quality property：例如 maintainability（要靠 review／inspection 評估），或者「冇 defect」（testing 只能證明有錯）。
易錯

「要等 implementation 完先可以諗 system test」係錯：諗（devise）test 同執行 test 係兩件事。

9. Unit、component（interface）同 system testing

一句講完

Unit：測單一 method／class（object class testing 要覆蓋所有 attribute、operation、state）；Component：測組合後嘅 interface；System：整合所有 component 測成個系統。

📑 Lecture 原 slide（6 張）＋逐張點睇（撳開）
點解 interface 要獨立測

每個 unit 單獨 OK，組合起嚟仍然會因為誤解介面而出錯。L9 列出 3 種 interface error：interface misunderstanding、interface misuse、timing errors。

圖解：4 種 interface
Interface 類型測咩指引
Message passing啱嘅 message 有冇以啱嘅方式到達用 stress testing
Procedural被 call 嘅 operation 有冇守 contract設計令 component 失敗嘅 test
Parameter傳／收嘅 data 啱唔啱參數用範圍兩端；pointer 用 null
Shared memory並發用戶睇到嘅 state 一致唔一致改變 component 啟動次序
例子

System testing policy（因為窮舉冇可能）：所有經 menu 用到嘅功能都要測；同一個 menu 嘅功能組合要測；有用戶輸入嘅功能，正確同錯誤 input 都要測。

易錯

Inheritance 令 object class testing 更難（要測嘅資訊唔集中喺一個 class）。System testing 係集體過程（collective），唔似 unit testing 個人做。

10. Regression testing 同 test automation（CI/CD）

一句講完

Regression testing：改完 code 之後再行舊 test，確保冇整爛之前 work 嘅嘢。因為人手做太慢，所以要自動化（JUnit、PyTest、Selenium），由 CI/CD pipeline 每次 push 自動行。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解

系統越大，改一處影響另一處嘅機會越高。自動化令每次改動都有成套 test 即時檢查，test 失敗就拒絕呢次改動。

流程圖 例子

PIM 項目：加咗「search by tag」，CI 自動行返全部 test，發現 delete 壞咗，呢次 push 被拒絕，問題喺到達用戶之前搵到。

易錯

Regression testing 唔係「測新功能」，係測舊功能有冇被新改動整壞。

11. Test-driven development（TDD，L3）

一句講完

TDD：先寫一個會 fail 嘅自動 test，再寫剛好夠令佢 pass 嘅 code，然後 refactor，保持所有 test 綠色；逐細步重複。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
點解要咁做

先寫 test 避免「test-lag」（test 追唔上 code）；寫 test 嘅同時就定義咗 interface 同行為 spec；每次加功能都自動行晒舊 test，即刻知道有冇整壞嘢。

圖解：TDD 循環 例子：2024 Q25(1) 答案要點
  1. Identify 一小步新功能（通常幾行 code 就做到）。
  2. 為佢寫一個自動化 test。
  3. 連同所有舊 test 一齊行：新 test 會 fail（因為未實作）。
  4. 實作功能，重新行所有 test，直到全部 pass；需要時 refactor。
  5. 全部 pass 之後先開始下一小步；整個開發就係呢個循環不斷重複（incremental）。
易錯

TDD 嘅問題（L3）：programmer 可能 test 寫得唔完整、偷工減料；有啲 test（例如複雜 end-to-end）好難逐步寫；好難判斷 test set 夠唔夠完整。

12. Release testing：requirements-based、scenario、performance

一句講完

Release testing 測一個準備俾開發團隊以外使用嘅版本，目標係說服 supplier 佢夠好。通常係 black-box，由 spec 出 test，由冇參與開發嘅獨立團隊做。

📑 Lecture 原 slide（6 張）＋逐張點睇（撳開）
三種做法
  • Requirements-based：每條 requirement 設計一個或多個 test（例如 Mentcare：病人對某藥敏感，開藥一定要出警告）。
  • Scenario testing：用典型使用情境（例如護士 George 家訪）一次過測好多功能。
  • Performance testing：逐步加 load 直到表現唔可接受；stress testing 刻意超載，睇系統點樣失敗。
圖解：performance vs stress 例子

Release testing 同 system testing 分別：system testing（開發期間）係 defect testing；release testing 係 validation testing，檢查系統符合 requirement、夠好俾外面用。

易錯

Release testing 屬於 system testing 嘅一種，但唔係由開發人員自己做。

13. User testing：alpha、beta、acceptance

一句講完

即使 system test 同 release test 做足，user testing 都係必要：用戶工作環境對 reliability、performance、usability、robustness 影響好大，而且喺開發環境複製唔到。

易錯

Agile 冇獨立 acceptance testing，但問題係嵌入團隊嘅用戶唔一定典型，代表唔到所有 stakeholder。

14. Static testing 同幾時停止 testing

一句講完

Static testing：唔行 code，檢查 code／requirement／design（inspection、walkthrough、自動 static analysis）。因為窮舉冇可能，要用指標決定幾時停 test。

📑 Lecture 原 slide（1 張）＋逐張點睇（撳開）
點解

Static testing 可以喺有 code 之前用，亦唔受錯誤互相遮蓋影響；「幾時停」要有客觀 exit criteria，唔可以靠感覺。

Static testing 都係 V&V 嘅一部分，唔需要執行程式。

  • 流程（TDD cycle）：

  • ② 先寫 automated test
  • ③ 行晒所有 test → 新 test fail
  • ④ 寫剛好夠嘅 code → 再行到 pass → refactor
  • ⑤ 下一段功能，重複
  • 好處：test 變成 regression test suite + 行為 spec
答案TDD interleaves testing and coding in small increments. First, identify a small increment of functionality that can be implemented in a few lines of code. Fourth, implement the functionality with just enough code and re-run all tests until they pass, refactoring the code while keeping all tests passing. Once all tests run successfully, move on to the next increment. The cycle repeats until all functionality is developed, so the tests also serve as a regression test suite and as a specification of behaviour.

1. Distinguish unit, component and system testing. (<80 words)

參考答案
🔑 記呢幾點就夠（流程＋關鍵詞）

九、常見疑問

Q：Partition 表要寫幾多行？表格空行數有冇提示？
冇提示（題目講明）。行數 = 決策樹入面做得到嘅葉數。寫多咗重複 class 或者漏咗都會扣分。
Q：一個條件有 ||／&&，要唔要拆開每個小條件？
唔使。題目定義嘅係「if condition expression evaluates to」：只睇成個條件嘅結果。
Q：冇行到嘅格寫咩？
寫 --（真卷範例就係咁寫）。唔好留空，亦唔好寫 F。
Q：Loop 條件點寫？
寫成個 test 期間出現過嘅所有值：一次都冇入 loop 寫 false；有入 loop 而最後因為條件 false 離開寫 true,false；如果用 break 離開而條件從未 false，就只寫 true（removeLDLetters 嘅 while 就係咁）。
Q：Expected result 要點寫？
逐行行一次 code 計出嚟，寫準確值（例如 0.20、"1/3/2024"、null、Exception）。
Q：Verification 同 validation 點記？
Verification：build the product right（對 spec）；Validation：build the right product（對客）。
Q：Alpha 同 acceptance testing 有咩分別？
Alpha 喺 developer 度同開發團隊一齊做，用喺 product 或 custom software；acceptance 係 custom system 嘅客用自己數據測，決定收唔收貨。
