二、筆記：由零講起

一分鐘重點
  • Analysis 講 WHAT（同實作無關）；design 講 HOW（實作導向藍圖）；programming 將藍圖變成 code。
  • Structured（PO）：function-first、top-down、圈動詞；DFD + ER model；structure chart。
  • OO：圈名詞；class、encapsulation、inheritance、polymorphism；CRC cards + GRASP；SOLID。
  • 兩種方法都追求 high cohesion、low coupling、information hiding。

1. Analysis vs design vs programming

一句講完

Analysis（狹義）：建立同實作無關嘅 analysis model，描述系統必須做咩、知道咩。Design：喺特定實作環境下滿足 requirement 嘅具體藍圖（唔一定可以執行）。Programming：將藍圖實現成可執行 source code。

點解要分

先搞清楚問題（唔受技術限制），再揀解決方法；混埋一齊會將設計決定偷偷塞入 requirement。

2. Structured（procedure-oriented）development

一句講完

一種 top-down、function-first 嘅方法：軟件係一堆分組成 function／procedure 嘅指令；著重動詞（系統做咩）；data 係被動、傳嚟傳去，logic 主動控制流程。

理論基礎
  • Dijkstra 1968「Go To Statement Considered Harmful」：無限制跳轉令邏輯難明 → structured control flow。
  • Wirth 1971「Stepwise Refinement」：將問題逐步細化。
  • Parnas 1972：用 information hiding 分 module，唔係按執行次序分。

易錯

Functional primitive 嘅條件：單一清楚目的；一份 mini-spec 寫得晒；input／output 穩定；唔需要 design 決定；用戶同分析員都明。

Leveling 同 balancing

Leveling：將一個 process 向下分解成 sub-process（Level-0 → 1 → 2）。Balancing：檢查邊界，每層嘅 input／output 一定要同上一層完全一樣（下層可以加 local data store）。

圖解：library Level-0（context）
Level內容

Level-1主要 process（1 Register member … 5 Return item）同 data store（D1 Member Records、D2 Item Catalogue、D3 Loans）
Level-2將 process 4 Checkout 拆成 4.1 Validate member … 4.5 Report outcome；可以加新 local store（D5 Loan Rules）
例子：DFD 講唔到嘅嘢

DFD 冇時間同次序嘅概念：「due date passes」呢類時間觸發、「每步都過先寫入」呢類次序，只可以寫喺 mini-spec 或者用 state machine。DFD 講資料去邊，唔講點樣決定一個值（規則放 mini-spec）。

易錯

Level-0 唔畫 data store（store 喺 bubble 入面）。只有 entity 同 store 可以重複畫，process 唔可以。下層多出一條邊界 flow = 冇 elicit 過嘅 requirement；少咗 = 漏洞。

5. Structured design：由 process 到 module（6 個 task）

一句講完

Design 決定邊個 module 擁有邊個 process、每個 module 守咩 contract。Input 係 analysis model（DFD、mini-spec、ER）。

6 個 task
  1. 每個 process 一個 owner → module list（雙向可追溯）。
  2. Top-down 排 module → structure chart。
  3. 寫每個 module 嘅 contract → IPO（input-process-output）spec。
  4. 定資料結構同擁有權 → record layout、parameter list。
  5. 指定內部邏輯 → pseudocode。
  6. 檢討質素、隱藏決定 → cohesion／coupling 檢查。
圖解：structure chart 例子：programming + testing

每個 module 變一個短、單一目的嘅 Python function；main driver 一個 loop：load data → show menu → read choice → dispatch → loop until quit。Testing 跟 structure chart：先 unit-test 葉，再 bottom-up 整合。

易錯

Design 只係組織，唔會發明新工作：每片葉都應該係 DFD 已有嘅 primitive。

Task 3–5 細節
  1. IPO contract（Task 3）：每個 module 寫 Input、Process、Output，加 pre-condition（call 之前要成立，例如 member_id 存在）同 post-condition（做完之後成立，例如 LOAN 已建立、ITEM 變 on loan）。
  2. Data structure（Task 4）：每個 record／table 有一個 owner module；資料經 parameter 傳，唔用 global variable（避免 common coupling）。
  3. Structured programming（Task 5）：pseudocode 只用三種 control construct：sequence、selection（if）、iteration（loop），唔用 goto（Dijkstra）。例如 checkout_item：validate_member → look_up_item → if available and under limit → create loan → else report error。
Over-decomposition

L7 警告：唔好按執行次序（step 1、step 2…）切 module，亦唔好拆到每個 module 得一兩行；咁會令 coupling 上升、cohesion 下降（同 Parnas 嘅論點一致）。

6. Cohesion 同 coupling

一句講完

Cohesion：一個 module／class 入面嘅元素有幾屬於一齊（越高越好）。Coupling：唔同 module 之間有幾互相依賴（越低越好）。

點解

High cohesion：一個 module 一件事，易明、易測、易重用。Low coupling：改動留喺局部，冇連鎖反應，module 可以獨立替換。

圖解：L7 兩個 checkout 設計 例子：OO 版本（L8）

Loan 只知道日期同 fine，從來唔 format UI 文字（high cohesion）；Catalog 用 message 同 Member、LibraryItem 溝通，唔掂佢哋內部（low coupling）。警號：一個 class 嘅職責要用「and」先講得晒。

易錯

減 coupling 嘅方法：用 parameter 傳資料、唔用 global；OO 偏好 composition 多過深層 inheritance。

7. Information hiding（Parnas KWIC）

一句講完

Module 嘅內部實作細節保密，外面只可以經穩定嘅 public interface 使用；分 module 嘅準則係隱藏每個 module 嘅設計決定（尤其最可能改嘅）。

KWIC 例子

KWIC（Key Word in Context）：讀入多行文字，每行做 circular shift，再按字母排序輸出。按執行次序分（Input、Shift、Alphabetizer、Output 共用 array）：一旦檔案太大要改用 database，所有 module 都要改。按 information hiding 分：用一個 line storage module 隱藏「資料點樣儲存」，其他 module 經 interface 存取，改儲存方式只影響一個 module。

圖解 例子：OO 嘅 encapsulation

LibraryItem 嘅 attribute 全部 private，只可以經 checkout()、giveBack() 改；object 自己守住「可唔可以借」、借書上限、due date 呢啲規則。

易錯

Information hiding 唔係「冇文件」：佢係隱藏實作，interface 要清楚公開。「Getters everywhere」（將所有內部用 getter 開放）違反佢（L8 pitfall）。

Encapsulation 同 least privilege

Attribute 用 private，經 public method 存取：外面唔可以亂改狀態（例如 Hero 嘅 health 唔可以俾外面設做負數）。Principle of least privilege：每個 module 只可以存取佢合法用途需要嘅資訊同資源。

9. Inheritance、polymorphism、abstract class、interface

一句講完

Inheritance：subclass 繼承 superclass（is-a）。Polymorphism：同一個 message，唔同 subclass 各自回應。Abstract class：有 abstract method、唔可以 instantiate。Interface：只定義 method signature，class implements 佢。

點解要

Polymorphism 取代 branching：唔使「if kind == BOOK … else if CD …」，加新種類只要加 subclass（L8：no kind field, no lookup table, no if-chain）。需要一個共同 origin 先可以 generic programming（一個 List 裝晒唔同種類）。

圖解：L8 item kinds {{UML:p7-poly}} 例子：Composite pattern（L7b）

Leaf 同 Composite 都係 Component；Composite 入面有一堆 Component（可以係 leaf 或者再一個 composite），call operation() 時遞迴轉發俾 children。用嚟表示樹狀結構（例如 folder 入面有檔案同 folder）。

{{UML:p7-composite}} 易錯

Abstract class 可以有 concrete method 同 attribute；interface（傳統 Java）只有 method signature 同常數。Abstract class 唔可以 new。

L7b 規則清單
  • 有最少一個 abstract method 嘅 class 一定要宣告 abstract。
  • Abstract method 會被繼承；subclass 如果冇實作晒所有 abstract method，自己都要宣告 abstract。
  • Abstract class 雖然唔可以 new，但定義咗一個 type：Shape[] shapes = new Shape[2]; 合法。
  • Interface：唔可以有 instance field；所有 instance method 都係 public abstract（兩個 keyword 可以省略）；寫 private method 或者有 body 都係 error。
  • Class 用 implements；interface 可以 extends 多個 interface（interface D extends A, B, C）。
  • Generic programming：用 polymorphic call heroes[i].fight() 代替 instanceof + cast 嘅 if-chain。

ISP 細節：Door extends TimerClient 會造成 interface pollution（Door 被迫有佢唔需要嘅 timeOut()）；Timer 一改（例如加 timeoutID），所有 Door 嘅 client 都要改：client 對 interface 有 backwards force，fat interface = 更多改變理由。解法：TimedDoor 經 DoorTimerAdapter（delegation）或者多重繼承 interface，「one interface for each responsibility」。DIP 例子：List<Hero> getHeros() 好過 ArrayList<Hero>（依賴 abstraction）。

OCP：「closure cannot be complete」：唔可能對所有改變都封閉，開頭作合理估計，之後 refactor。DIP 兩句：高層同低層都依賴 abstraction；abstraction 唔依賴細節，細節依賴 abstraction。

三、完整示範：用 SOLID 改 code（OCP + DIP）

一分鐘重點
  • 見到 instanceof if-chain、或者高層 class 直接 new 低層 concrete class，就諗 OCP／DIP：抽 interface。

Step 1：原本 code（違反 OCP）

for (Object s : shapes) {
  if (s instanceof Circle)      ((Circle) s).drawCircle();
  else if (s instanceof Rectangle) ((Rectangle) s).drawRectangle();
}
  1. 問題：每加一種 shape（例如 Triangle）都要改呢個 loop → 唔係 closed for modification。
  2. 改法：定義 interface Shape { void draw(); }，每種 shape implements 佢。
  3. 結果：loop 變 for (Shape s : shapes) s.draw();，加 Triangle 只要加新 class（open for extension）。已用 Java 跑過：輸出 circle rect triangle。

Step 2：Progress（違反 OCP + DIP）

class Progress {
  private File f;                         // 直接依賴 concrete File
  int getAsPercent() { return f.getSent() * 100 / f.getLength(); }
}
  1. 問題：想顯示「長計算」嘅進度，要改 Progress。高層（Progress）依賴低層細節（File）。
  2. 改法：interface Measurable { int getTotal(); int getPartial(); }；File、Computation implements；Progress 只持有 Measurable。
  3. 驗證（Java 跑過）：File(200, 100) → 50%；Computation(8, 2) → 25%；Progress 一行都冇改。

考試見到「新增一種 X 要改舊 code」就答 OCP；見到「高層直接用低層 concrete class」就答 DIP，兩個嘅解決方法都係抽 interface／abstraction。

四、Past paper 全答 + 預測題

2022 Q23(3) · Dependency Inversion · 5 分 · L8

In conventional layered architecture, a high-level layer depends directly on the layer beneath. The DI principle proposes against this. Explain what it proposes instead and why. (<120 words)

參考答案
答案DI proposes that high-level modules should not depend on low-level modules; both should depend on abstractions such as interfaces, and abstractions should not depend on details—details should depend on abstractions. For example, an EBookReader depends on an EBook interface that PDFBook and other book classes implement, instead of depending directly on PDFBook. The reason is that direct dependence on lower-level components limits the reusability of higher-level components and forces them to change whenever the lower-level implementation changes. With abstractions in between, low-level implementations can be replaced or added without modifying the high-level policy, so the layers are decoupled and easier to reuse and test.

預測題 1 · SRP · 4 分

A class Report has methods calculateTotals(), formatAsHtml() and saveToDatabase(). Which SOLID principle does it violate? How should it be redesigned? (<80 words)

參考答案
答案It violates the Single Responsibility Principle: the class has three reasons to change (business calculation, presentation format and persistence), so these responsibilities become coupled. It should be split into Report (calculating totals), a ReportFormatter interface with implementations such as HtmlFormatter, and a ReportRepository that saves reports, so each class changes for only one reason.
預測題 2 · Analysis vs design · 4 分

Compare software analysis and software design in terms of purpose, key question and orientation. (<80 words)

參考答案
答案Analysis aims to understand and specify the essence of the problem; its key question is what the system must do and know, and it is implementation-independent, conceptual and not executable. Design aims to construct a concrete solution; its key question is how the system will do it, and it is implementation-specific, covering architecture, components, interfaces, algorithms and data structures that can be translated into code.
預測題 3 · DFD balancing · 3 分

What are leveling and balancing in data flow diagrams? Why is balancing important? (<80 words)

參考答案
答案Leveling decomposes a process into sub-processes in a lower-level DFD (Level-0 → Level-1 → Level-2). Balancing checks that the inputs and outputs at the boundary of a lower-level diagram exactly match those of its parent process. It is important because an extra boundary flow at a lower level indicates an un-elicited requirement, while a missing one indicates a hole in the decomposition.

八、短答題

1. Explain cohesion and coupling and why good designs aim for high cohesion and low coupling. (<80 words)

參考答案
答案Cohesion measures how strongly the elements inside a module belong together; coupling measures how much modules depend on each other. High cohesion gives each module one clear job, making it easier to understand, test and reuse. Low coupling means modules share minimal internal knowledge and communicate through parameters or messages, so changes stay local without ripple effects and modules remain independent and replaceable.

2. What is information hiding? Illustrate with the KWIC example. (<80 words)

參考答案
答案Information hiding keeps a module's implementation details secret and exposes them only through a stable interface; modules should be decomposed by hiding design decisions likely to change. In KWIC, decomposing by processing steps lets all modules share the line array format, so switching to a database changes every module. Hiding storage behind a line-storage module confines that change to one module.

3. Distinguish method overloading and method overriding. (<60 words)

參考答案
答案Overloading declares several methods with the same name but different parameter lists in the same class; the call is resolved at compile time. Overriding is when a subclass redefines a method inherited from its superclass with the same signature; the version executed is chosen at run time according to the object's actual type (polymorphism).

九、常見疑問

Q：L7 未出過長題，要唔要溫？
要識 T/F 程度：DFD 符號、leveling／balancing、動詞分層、cohesion／coupling、information hiding。佢係今年先加嘅課，冇舊題，所以出 T/F 嘅機會唔細。
Q：GRASP 要背晒 9 個？
最重要：Information Expert、Creator、Controller（亦係答 class diagram 放 operation 嘅理由）。其餘 4 個（Polymorphism、Pure Fabrication、Indirection、Protected Variations）識認就得。
Q：DIP 同 layered architecture 有咩關係？
傳統 layered：高層直接依賴下一層。DIP：兩層之間加 abstraction（interface），高層依賴 interface，低層實作 interface，令高層可以重用、低層可以替換。
Q：Abstract class 同 interface 揀邊個？
有共享 code 同 state（例如 LibraryItem 嘅 itemId、checkout()）用 abstract class；只係定義能力（例如 Shape.draw()、Measurable）用 interface。
