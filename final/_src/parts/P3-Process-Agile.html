「贊成／反對 agile」答題步驟

  1. 第一句答立場（2 分）：「I am against using an agile approach as the main approach.」
  2. 喺情境搵線索：requirement 穩唔穩定？有冇硬件／合約固定？系統大唔大、幾長命？幾多間公司？要唔要 safety certification？客可唔可以長期參與？
  3. 每個理由對應 lecture 一句：例如「critical systems need extensive safety analysis」（L2 waterfall 適用）、「contract, governance and risk mismatch」（L3 agile 問題）。
  4. 每個理由一句情境 + 一句原因，守字數。

二、筆記：由零講起

一分鐘重點
  • 所有 process 都有 4 個活動：specification、development、V&V、evolution。
  • 3 個 process model：waterfall（plan-driven）、incremental、integration & configuration（reuse）。
  • 應付改變：change anticipation（prototyping）同 change tolerance；incremental delivery 兩樣都支持。
  • CMMI 5 級：Initial → Managed → Defined → Quantitatively Managed → Optimizing。
  • Agile：manifesto 4 句、5 個 principle；XP practices；Scrum（product owner、ScrumMaster、sprint、backlog）。

1. Software engineering 係咩；好軟件有咩特質（L1）

一句講完

SE 係一門工程學科，處理軟件生產嘅所有方面：技術開發過程、支援工具同方法，同埋 project management。

📑 Lecture 原 slide（6 張）＋逐張點睇（撳開）
點解需要

現代世界靠軟件運作，要經濟又快咁整出可靠嘅軟件。軟件維護成本通常高過開發成本，所以長遠用 SE 方法更平。Software crisis 未解決：Standish Chaos Report 2020：約 31% 成功、50% challenged（遲、超支、減功能）、19% 失敗。

圖解：越遲修 bug 越貴
好軟件特質意思
Acceptability目標用戶接受：易明、易用、同佢哋其他系統兼容
Dependability可以信賴：reliability、availability、safety、maintainability、fault tolerance
Trustworthiness用戶同社會應該信佢：security、privacy、透明、合規、可預測
Efficiency唔浪費資源：反應時間、處理時間、資源使用
例子：FAQ

Software = 程式 + 相關文件。SE vs computer science：CS 重理論同基礎，SE 重實際開發同交付。SE vs system engineering：system engineering 包括硬件、軟件、process，SE 係其中一部分。Maintenance 分四類：corrective（修 bug）、adaptive（適應環境）、perfective（改善）、preventive（預防）。

易錯

冇一套「最好」嘅技術適用所有系統：要按應用類型、客需要、團隊背景揀（SE diversity）。

L1：歷史同經濟角度

歷史：SE 呢個名喺 1968 NATO 會議提出，起因係 software crisis（遲交、超支、有 bug）。L1 話 crisis 到今日都未解決：Standish Chaos Report 2020 約 31% 成功、50% challenged、19% failed。

經濟：新 coding technique CTnew 快 10%（即平 10%），應唔應該用？常識答「梗係用」；SE 答案要計埋培訓成本、引入新技術嘅影響、對 maintenance 嘅影響。即係睇成個 lifecycle 嘅成本，唔係淨係開發成本。

2. SE ethics 同 ETHICS-PLUS model（L1）

一句講完

軟件工程師嘅責任超越技術同法律：ACM／IEEE-CS 嘅 SE Code of Ethics 有 8 個 principles；遇到兩難可以用 HKIE 嘅 ETHICS-PLUS 模型分析。

📑 Lecture 原 slide（5 張）＋逐張點睇（撳開）
點解

Ethical conduct 唔止係守法；專業信任要靠誠實、透明、負責任。軟件工程師應該以公眾利益行事。

流程圖：ETHICS 六步 + PLUS 四個過濾 例子：L1 dilemmas
  • 管理層要求為趕 launch 跳過關鍵 testing 或者忽略保安漏洞 → clauses 1.03、3.10。
  • 老闆要你偷偷收集用戶資料、用 dark pattern → principle 2、clauses 3.12、1.06。
  • ML model 對某族群有偏見、唔考慮殘疾人士 → clauses 1.07、4.03。
8 個 principles（Code 全文，L1 slide 20）
Principle意思
1 PUBLIC行事要符合公眾利益（最重要，其他都要「consistent with the public interest」）
2 CLIENT AND EMPLOYER為客戶同僱主最佳利益做事，但唔可以違反公眾利益
3 PRODUCT產品同修改要達到最高專業標準

L1 dilemmas 用到嘅 clauses：1.03 只批准有充分理由相信安全、符合 spec、通過測試、唔損害私隱同環境嘅軟件；1.06 公開陳述要公平、唔可以欺騙；1.07 考慮殘疾、經濟弱勢等會減少用軟件機會嘅因素；3.10 確保足夠嘅 testing、debugging 同 review；3.12 開發尊重受影響人士私隱嘅軟件；4.03 評估軟件時保持專業客觀。

個人層面（L1 Practicing the Principles）：唔偷資料謀私利；唔分發或出售工作得到嘅 proprietary 資料；唔用電腦科技助長歧視或騷擾。

易錯

「Ethics = 守法」係錯：L1 話 ethical conduct transcends legal compliance。Code 由 IEEE-CS 同 ACM 批准；適用於 practitioners、educators、managers、policymakers，連 trainees 同 students 都包。Code 唔係一條會自動出答案嘅「ethical algorithm」，要用判斷。

3. Software process：4 個基本活動；plan-driven vs agile

一句講完

Software process 係開發軟件所需嘅一套有結構嘅活動。所有 process 都包括：specification（定義要做咩）、development（design + implementation）、V&V（檢查符合 spec 同需要）、evolution（因應需要改變）。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
點解要 process

「You cannot test quality into a product; you must build it in.」Process 將個人英雄主義變成機構能力，提供審計基礎，管理複雜度。Process 描述仲可以包括 products（交付物）、roles（角色）、pre/post-conditions。

圖解 例子：plan-driven vs agile
Plan-drivenAgile
計劃所有活動預先計劃逐步（incremental）計劃
進度量度同原本計劃比睇交付咗幾多可用軟件
改變代價高容易
實際大部分 process 兩樣都有；冇絕對啱或錯嘅 process
易錯

Evolution 唔係「開發完先開始」：L2 話 development 同 evolution 嘅界線越嚟越唔重要，因為好少系統係全新。

4. Waterfall model

一句講完

Waterfall 有分開嘅 phase：requirements analysis & definition → system & software design → implementation & unit testing → integration & system testing → operation & maintenance；原則上一個 phase 完成先去下一個。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解難應付 requirement 改變

Project 被硬性切成獨立階段，requirement 喺第一個 phase 已經「凍結」；後期先發現要改，就要返轉頭改晒之前所有文件同設計，成本好高。所以只適合 requirement 清楚、改變有限嘅情況（好少商業系統係咁穩定）。

圖解 例子：適合 waterfall 嘅系統（L2）
  1. Embedded systems：軟件要同硬件 interface，硬件唔可以隨時改（例如 Asm1 嘅胰島素泵）。
  2. Critical systems：需要對 spec 同 design 做大量 safety／security analysis（例如醫療、航空）。
  3. 大型系統，屬於更大嘅工程系統，由幾間 partner 公司合作開發（例如 2022 嘅城市交通系統）。
易錯

Waterfall 嘅 maintenance 係最後一個 phase；L1 講 classical view「development-then-maintenance」已經過時：maintenance 可以喺 deploy 之前已經發生。

5. Incremental development

一句講完

先整一個初步版本，收用戶反饋，再逐個版本演化，直到完成。可以係 plan-driven、agile 或者混合；每個 increment 唔一定要交俾客。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
好處同問題
BenefitsProblems
容易收客對已完成部分嘅反饋需要更強嘅 configuration management 同 project 協調
應付 requirement 改變嘅成本降低初始 architecture 要夠靈活，加新部分唔可以整壞舊功能
更快交付同部署有用嘅軟件加越多 increment，系統結構越容易退化
圖解 例子

PIM 項目：第一個版本只做 task 增刪；收到組員反饋後加 search；再加 contact 同 event。每個版本都可以行，但唔一定交俾老師。

易錯

Incremental development（開發方式）同 incremental delivery（將 increment 真係交俾客用）唔同：後者係 coping with change 嘅方法（概念卡 7）。

6. Integration and configuration（reuse-oriented）

一句講完

由現有 component、application system 或者 COTS（commercial off-the-shelf）系統整合出新系統，再配置佢哋嘅行為去配合用戶需要。而家好多商業系統都係咁整。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
好處同壞處
  • ✓ 少啲由零開始寫，成本同風險降低；交付同部署更快。
  • ✗ Requirement 一定要妥協，系統可能唔完全符合用戶真正需要；對系統演化失去控制（新版本由供應商決定）。
圖解：可重用軟件 3 類 例子

學校用現成嘅 Canvas（COTS）加配置，而唔係自己寫 LMS：快、平，但某啲功能要遷就 Canvas 嘅做法，而且升級時間由 Instructure 決定。

易錯

Reuse 嘅缺點唔係「質素一定差」，係 requirement 妥協同失去演化控制。

7. Coping with change：moving target、anticipation、tolerance

一句講完

大型項目一定有改變。Moving target problem：開發期間 requirement 不斷變，而且冇根治方法。減少 rework 成本有兩個方向：change anticipation（預早發現要改咩）同 change tolerance（令改動成本低）。

📑 Lecture 原 slide（2 張）＋逐張點睇（撳開）
點解要咁做

改變成本包括 rework（重做已完成嘅嘢）同實作新功能；越遲改越貴。

圖解 例子：點解 incremental delivery 兩樣都支持（2024 Q21(1)）
  1. Anticipation：用戶喺早期 increment 試用系統，好早就發現佢哋真正想要咩，之後 increment 嘅 requirement 可以跟住調整。
  2. Tolerance：每個 increment 細、而且開發一個 increment 時只凍結嗰個 increment 嘅 requirement；改變可以放入之後嘅 increment，成本低。
易錯

Prototyping 唔係 change tolerance：prototype 通常用完就掉（throwaway），佢只係幫你「預早知道」。

8. Prototyping 同 incremental delivery：好處同問題

一句講完

Prototype：快速整嘅初版，用嚟示範概念、試設計、了解問題。分 throwaway（rapid）同 evolutionary（breadboarding）。金句：「Prototype just enough to learn, but not enough to ship.」 Incremental delivery：將開發同交付拆做 increment，每個交付部分功能。

📑 Lecture 原 slide（4 張）＋逐張點睇（撳開）
Incremental delivery 點運作

用戶 requirement 排優先次序，最高優先嘅放最早嘅 increment；一個 increment 開始開發，佢嘅 requirement 就凍結，但之後 increment 嘅 requirement 仲可以改。

圖解：increment 時間軸 例子：兩張清單（2025 Q21(2) 考）
PrototypingIncremental delivery
好處澄清模糊 requirement；早期用戶反饋；增加持份者支持；減少 rework；降低風險早期持續交付價值；更快 ROI 同現金流；降低風險；反饋循環好；整合衝擊細；士氣好
問題持份者誤解（以為 prototype 係成品）；scope creep；前期時間成本增加；analysis paralysis；虛假安全感；evolutionary code rotArchitecture 侵蝕（最大風險）；管理同 CI/CD 負擔重；scope creep；只有部分功能令用戶沮喪；文件難管理；固定價合約難處理
易錯

2025 Q21(2) 問嘅係「compared with a non-iterative process」：答好處時要對比 waterfall（例如 waterfall 要等到最後先有可用軟件）。

9. Process improvement：performance、capability、maturity；CMMI

一句講完

Performance：某個 project 實際做到嘅結果；capability：某個 process 重複做時可預期嘅結果範圍；maturity：成個機構將 process 制度化、文件化、優化嘅程度。CMMI V2.0 定義 5 個 maturity level。

📑 Lecture 原 slide（5 張）＋逐張點睇（撳開）
L2 嘅比喻：交通
  • Performance = 你今朝實際用咗幾耐返工（變化大）。
  • Capability = 「95% 嘅行程喺 30–40 分鐘之內」（可預測範圍）。
  • Maturity = 城市規劃署有冇標準政策、同步燈號、中央指揮中心（制度）。
圖解：CMMI 5 級樓梯
Level機構狀態結果
1 Initial被動、冇文件、靠個人英雄唔可預測，成功靠運
2 ManagedProject 層面計劃、追蹤、控制（requirement、planning、monitoring）同一團隊／project 可以重複，跨 project 唔穩定
3 Defined全機構標準 process、共同培訓無論邊隊做都穩定
4 Quantitatively Managed用統計方法（例如 Six Sigma）控制 sub-process表現喺嚴格數量範圍內
5 Optimizing用 level 4 數據主動改進持續改善，消除最差情況
例子：staged vs continuous（2023 Q21(4)）
  1. Staged：定一個戰略目標「達到 maturity level X」，然後系統地改善嗰級要求嘅所有 practice area。結果用一個 maturity level 表示。
  2. Continuous：benchmark 同診斷 → 按業務需要揀優先 → 實施 → 量度改善；機構自己揀個別 practice area，提升佢哋嘅 capability level（0–5）。
易錯

Maturity level 係 1–5（成個機構）；capability level 係 0–5（個別 practice area）。2023 Q21(3) 排序答案：Managed < Defined < Quantitatively Managed。QA 係確保 CMMI 嘅要求真係做到、提供 appraisal 證據嘅機制。

Quality Assurance（QA，L2）

QA = 識別、計劃、採用同實施確保產品滿足用戶所需嘅 discipline 同行動（即 process）。分工：CMMI 話機構要做咩先達到 process maturity；QA 係確保真係做咗嘅機制，並提供 appraisal 需要嘅客觀證據。做法例子：用 error analysis 同 trend analysis 搵出各個 process 嘅弱點。

10. Agile：manifesto、5 個 principles、適用範圍

一句講完

Agile 為咗減少 process overhead（例如少啲文件），快速應付 requirement 改變；所有 agile 方法都主張逐步開發同交付。

📑 Lecture 原 slide（3 張）＋逐張點睇（撳開）
點解出現

1980–90 年代 plan-driven 方法嘅 overhead 太大（嗰啲方法原本為大型、長命系統而設，例如航空、政府系統）。

圖解：Agile Manifesto（左邊更重要，但右邊都有價值）
5 個 principles意思
Customer involvement客全程參與，提供同排序 requirement，評估每個 iteration
Incremental delivery逐個 increment 開發，客決定每個 increment 包含咩
People not process認同團隊技能，俾佢哋自己決定工作方式
Embrace change預期 requirement 會變，設計系統去容納
Maintain simplicity軟件同 process 都保持簡單，主動消除複雜度
例子：agile 適合邊類
  1. 軟件公司開發中小型產品出售（而家大部分 app 都用 agile）。
  2. 機構內部 custom system，條件係：客承諾參與開發，同埋外部規管少。
易錯

Agile 唔係「冇文件」：manifesto 話右邊都有價值，只係左邊更重要。

11. Extreme Programming（XP）practices

一句講完

XP 將好嘅做法推到「極端」：一日 build 幾次、每 2 星期交付一次、每次 build 要所有 test 過。主要 practices：user stories、refactoring、TDD、pair programming。

📑 Lecture 原 slide（6 張）＋逐張點睇（撳開）
各 practice 點解
  • User stories（「As a <role> I can <capability>, so that <benefit>」）：3 個 C = Card、Conversation（L3 寫 Communication）、Confirmation。易明，但難判斷 story 夠唔夠覆蓋晒 requirement。
  • Refactoring：主動改善 code（改名、抽 method），即使冇即時需要。XP 認為「design for change」唔值得，因為改變冇辦法可靠咁預計。
  • Pair programming：兩人一部機；支持 collective ownership、等於非正式 review、鼓勵 refactoring、未必冇效率。
  • TDD：見 P2 概念卡 11。
圖解：XP practice → agile principle（2024 Q21(2) 考） 例子：XP 其他 practices
Practice意思
Incremental planningrequirement 寫喺 story card，按時間同優先揀入 release
Small releases先做最少而有商業價值嘅功能，頻繁 release
Simple design只做到滿足現時 requirement 嘅設計，唔多做
Collective ownership大家都可以改任何 code，冇「專家孤島」
Continuous integration完成一個 task 即刻整合，所有 unit test 一定要過
Sustainable pace唔接受大量 OT：長遠會降低 code 質素同生產力
On-site customer用戶代表全職陪 XP 團隊
易錯

XP 技術導向，好難融入一般機構管理，所以原版 XP 唔普及，但佢嘅 practices 被廣泛採用。XP 冇外部 testing 團隊可以用嘅 system spec：user story 唔係 system requirement。

12. Scrum：agile project management

一句講完

Scrum 專注管理 iterative 開發（唔係指定技術 practice）。三個 phase：outline planning（目標 + architecture）→ 一連串 sprint cycle → project closure（文件、總結經驗）。

📑 Lecture 原 slide（5 張）＋逐張點睇（撳開）
點解要 Scrum

Plan-driven 管理需要 visibility；早期 agile 嘅非正式計劃同呢個需要衝突。Scrum 用固定長度 sprint、backlog、每日 Scrum 提供 visibility 同控制。

圖解：sprint cycle
術語意思
Development team自組織，≤ 7 人
Product owner搵 feature、排優先、持續 review product backlog

1) Describe the waterfall model, 2) state why it is difficult for it to handle changing requirements, 3) describe one type of system suitable for it and explain why.

2025 Q21(2) · 4 分 · <100 words · L2

Name two benefits and two problems of incremental delivery, compared with a non-iterative process.

參考答案
答案Benefits: 1) Customers receive useful functionality early and continuously, instead of waiting until the end, so value and return on investment come sooner. 2) Early increments act as prototypes, giving feedback that reduces the risk of building the wrong system and lowers overall project risk. Problems: 1) Architectural erosion: as increments are added, the system structure tends to degrade unless the initial architecture is flexible. 2) It is hard to use with fixed-price contracts and requires heavier management, configuration and integration effort, because the full specification is not known up front.
2025 Q21(3) · 4 分 · <100 words · L3

Compare the product backlog and the sprint backlog in terms of 1) what they contain and 2) what changes may occur during a sprint.

參考答案
答案1) The product backlog is the list of all to-do items for the whole project: features, requirements, user stories and supplementary tasks such as architecture definition and documentation. The sprint backlog contains only the items selected from the product backlog to be developed in the current sprint. 2) During a sprint, the product backlog may change: the product owner can add, remove or reprioritize items. The sprint backlog is essentially fixed once the sprint starts; the team is isolated from outside changes and only updates the progress of its items.
2025 Q21(4) · 2 分 · <50 words · L3 · 選項缺頁

At the end of a 12-day sprint only 80% of tasks are done (constant speed). Which of the two options is appropriate according to Scrum? Why?

注意卷上冇印出兩個選項。按題意（「constant speed」），兩個選項好可能係：(a) 延長 sprint 3 日去做完（12 × 20% ÷ 80% = 3 日）；(b) sprint 準時結束，未完成嘅 task 返去 product backlog，下個 sprint 按實際 velocity 計劃。以下按 Scrum 原則答。
參考答案
答案End the sprint on schedule and return the unfinished tasks to the product backlog. In Scrum, sprints are fixed-length, so the sprint is not extended; the shortfall is used to adjust the team's velocity when planning the next sprint.

(1) Describe change anticipation and change tolerance, and explain why incremental delivery supports both. (<100 words, 6 points)

參考答案
答案Change anticipation: the process includes activities that can foresee possible changes before significant rework is needed, e.g., showing a prototype to customers. Change tolerance: the process is designed so that changes can be accommodated at relatively low cost, normally through incremental development. Incremental delivery supports anticipation because users experiment with early increments and refine their requirements for later ones; it supports tolerance because only the current increment's requirements are frozen, so changes go into later increments and affect only a small part of the system.

(3) Explain what refactoring is and give two reasons for its necessity in XP. (<100 words, 4 points)

參考答案
答案Refactoring is continuously improving the internal structure of code without changing its behaviour, e.g., renaming attributes and methods or replacing inline code with calls to library methods, even when there is no immediate need. Reasons: 1) XP does not design for change, because changes cannot be reliably anticipated; refactoring keeps code well-structured so that changes are easy when they arrive. 2) Frequent incremental local changes degrade software structure and readability; refactoring restores understandability and reduces the need for documentation.
2023 Q21 · CMMI · 15 分 · L2
📄 原卷題目截圖：2023 Q21 · CMMI（15 分）（撳開）

1) Explain (a) process performance (b) process capability (c) process maturity. (<100 words, 6 points)

參考答案
答案(a) Performance is the actual, observable result of a specific project or activity, measured by indicators such as cycle time, defect density, cost and customer satisfaction. (b) Capability is the predictable range of results that a specific process can produce when it is run again, i.e., how consistent its performance is. (c) Maturity is the degree to which an organization has institutionalized, documented and optimized its processes across the whole enterprise.

2) Key characteristics of (a) Defined (b) Quantitatively Managed (c) Managed. (<100 words, 3 points) 3) Sort them in increasing maturity. (3 points)

參考答案
答案(a) Defined: processes are standardized across the entire organization with a common training curriculum and process framework, so performance is consistent regardless of the team. (b) Quantitatively Managed: statistical and quantitative techniques are used to control sub-processes, keeping performance within quantitative bounds. (c) Managed: processes are planned, tracked and controlled at the project level, so success can be repeated on similar work by the same team.
3) Managed < Defined < Quantitatively Managed.

4) Key difference between the staged and continuous representations of CMMI. (<100 words, 3 points)

參考答案
答案The staged representation sets an organization-wide goal of reaching a specific maturity level and systematically improves all the practice areas that level requires, so progress is described by one maturity level (1–5). The continuous representation lets the organization select individual practice areas according to its business priorities and raise their capability levels (0–5) independently, so progress is described by a capability profile across practice areas.

八、短答題

1. Compare throwaway and evolutionary prototyping. (<60 words)

參考答案
答案A throwaway (rapid) prototype is built quickly to clarify requirements or test design options and is then discarded; the real system is built properly. An evolutionary prototype is developed and refined until it becomes the delivered system. Evolutionary prototyping risks code rot, since quick-and-dirty code is carried into the product.

2. Why may agile methods be unsuitable for maintaining a large legacy system? Give two reasons. (<80 words)

參考答案
答案1) Maintenance work is interrupt-driven (urgent bug fixes, support requests), which conflicts with planning work in fixed sprints. 2) Legacy systems often lack a clear product owner and documentation, and their old code and architecture constraints create high regression risk, while agile minimizes documentation needed for long-term handover and compliance.

3. What are the roles of the product owner and the ScrumMaster? (<60 words)

參考答案
答案The product owner identifies product features or requirements, prioritizes them and continuously reviews the product backlog to meet business needs. The ScrumMaster ensures the Scrum process is followed, arranges daily meetings, tracks the backlog, communicates with customers and management, and protects the team from outside interference.

4. Describe the three phases of Scrum. (<60 words)

參考答案
答案1) Outline planning: establish the general project objectives and design the software architecture. 2) A series of sprint cycles, each developing an increment of the system. 3) Project closure: wrap up the project, complete the required documentation such as help frames and user manuals, and assess the lessons learned.

九、常見疑問

Q：「贊成／反對 agile」可唔可以答贊成？
可以，只要理由同情境配合。不過真卷嘅情境（大型、多公司、safety-critical、硬件固定）明顯偏向反對，官方 solution 都係反對。
Q：Incremental development 同 incremental delivery 有咩分別？
Development 係開發方式（版本不斷演化，唔一定交俾客）；delivery 係真係將每個 increment 交俾客用，係 coping with change 嘅方法。
Q：CMMI 一定要背晒 5 級？
要。2023 考咗 3 個 level 嘅特徵同排序；最易混係 Managed（project 層面）同 Defined（全機構）。
Q：XP practice 對 agile principle 有冇一對多？
有：small releases → incremental delivery + embrace change；refactoring → embrace change + maintain simplicity。考試答 L3 列出嘅其中一個就得。
Q：Velocity 係咪越高越好？
Velocity 係估計工具，用嚟計劃同量度改善；唔同團隊之間唔應該直接比較。
